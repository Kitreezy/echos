# ADR 001. Свой WebSocket-клиент вместо Starscream

Принято 09.09.2026. Спайк — ветка `spike/starscream_comparison`, в `main` не идёт.

## Вопрос

Клиент написан на `URLSessionWebSocketTask`. Не стоило ли взять Starscream?

Чтобы ответить не на глаз, транспорт отделили протоколом `RawWebSocket`
(открыть, отправить, получить, пинг, закрыть), сделали за ним вторую
реализацию и прогнали один набор сценариев против трёх конфигураций:
свой клиент, Starscream со своим движком и Starscream поверх
`URLSessionWebSocketTask`.

Третья нужна потому, что у Starscream два движка, и по умолчанию работает
не тот, о котором обычно думают: `useCustomEngine` равен `true`, то есть
включается собственный фрейминг `WSEngine`. Обёртку над `URLSessionWebSocketTask`
(`NativeEngine`) надо просить явно.

## Что получилось

Транспорта в клиенте — 110 строк из 458. Реализация на Starscream заняла 92,
то есть экономия 18 строк: библиотеку всё равно надо оборачивать под свой
интерфейс.

Остальные 348 строк — реконнект с откатом и джиттером, heartbeat с таймаутом
на pong, очередь исходящих, реакция на `NWPathMonitor`, повторное
представление серверу после переподключения. Ничего из этого Starscream не
делает: он присылает событие `.reconnectSuggested`, то есть подсказку, а
политику пишете вы.

Все 8 сценариев прошли во всех трёх конфигурациях — подключение, обмен,
возврат после падения сервера, heartbeat, пауза без сети, мгновенный реконнект,
доставка отложенного сообщения. Ни один не показал преимущества библиотеки.

## Два неприятных момента

**Падение под Swift 6.** Вот такой код роняет процесс:

```swift
await withCheckedContinuation { continuation in
    socket.write(data: data) { continuation.resume() }
}
```

`EXC_BREAKPOINT` в `dispatch_assert_queue_fail`. Колбэк объявлен как
`(() -> ())?`, без `@Sendable`, поэтому компилятор считает его унаследовавшим
изоляцию главного актора от вызывающего метода. А зовёт его библиотека со своей
очереди — и проверка исполнителя срабатывает. Компилятор молчит: тип колбэка
ничего не обещает. Лечится явным `@Sendable` у замыкания, но узнать об этом
можно только наткнувшись. Риск общий для всех колбэков Starscream — API
писался до строгой конкурентности.

**Потеря отправки.** `WSEngine.write` при `canSend == false` просто выходит,
не вызвав completion. Отправка теряется молча: ни ошибки, ни колбэка. Наша
реализация в этой ситуации бросает.

## Что Starscream действительно даёт

Сжатие `permessage-deflate` — `URLSession` его наружу не выставляет вообще.
Это единственное настоящее преимущество, остальное вопрос вкуса: своё
наблюдение за живучестью пути у нас уже есть в `NetworkMonitor`, pinning у
`URLSession` решается делегатом, а поддержка iOS 12 не нужна.

Для echos сжатие бесполезно: по сокету ходят короткие JSON-конверты.

## Решение

Остаёмся на `URLSessionWebSocketTask`.

Библиотека покрывает четверть кода, экономит 18 строк, не закрывает ни одного
сценария, требует ручного обхода трапа под Swift 6 и молча теряет отправки при
неготовом соединении. Плюс 2766 строк чужого кода в зависимостях.

Стоит вернуться к вопросу, если понадобится сжатие, потребуется тонкий контроль
фрейминга или `URLSessionWebSocketTask` сломается в очередной версии iOS.

## Что осталось от спайка

`RawWebSocket` и контрактные тесты. Разделение «транспорт отдельно, политика
живучести отдельно» полезно само по себе, а тесты теперь можно натравить на
любую следующую реализацию.
